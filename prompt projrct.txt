# 5. CORE PROBLEMS TO SOLVE

## Problem 1 — Long physical queues

Students currently waste time standing in line to place orders.

### Required solution

Online ordering + digital queue + scheduled pickup.

The system should separate:

ORDERING QUEUE

from:

FOOD PREPARATION QUEUE

and:

PICKUP QUEUE.

---

## Problem 2 — Food preparation/pickup waiting

Students often do not know when their food will actually be ready.

### Required solution

Provide live:

* order status
* orders ahead
* kitchen workload
* estimated preparation time
* estimated ready time
* pickup window

ETA must update when operational conditions change.

---

## Problem 3 — Peak-time crowd

Campus breaks can create sudden demand spikes.

The system must detect and respond to congestion.

Example:

CURRENT:

* 48 active orders
* kitchen capacity = 25
* workload = HIGH

The system should not blindly accept unlimited orders.

It should intelligently manage:

* pickup slots
* capacity
* expected preparation time
* order admission
* user recommendations

Example:

12:30–12:40 → FULL
12:40–12:50 → HIGH
12:50–1:00 → AVAILABLE
1:00–1:10 → LOW

The user should receive an intelligent pickup recommendation.

---

## Problem 4 — Payment problems

Payment must be treated as a reliable backend workflow, not merely a frontend button.

Support payment states such as:

INITIATED
PROCESSING
SUCCESS
FAILED
PENDING
TIMEOUT
CANCELLED
REFUNDED

Never confirm an order solely because the frontend reports success.

Payment confirmation must be verified through the authoritative payment mechanism available to the project.

Implement idempotency where necessary to prevent:

PAY → PAY

from creating duplicate orders.

---

## Problem 5 — Manual management

Replace manual workflows with dedicated operational interfaces.

Student:

ORDER → PAY → TRACK → PICKUP

Kitchen:

RECEIVE → ACCEPT → PREPARE → READY

Pickup:

READY → QR VERIFY → COLLECTED

Admin:

MONITOR → ANALYZE → CONTROL → REPORT

# 12. DYNAMIC ETA ENGINE

Implement an initial deterministic ETA engine.

ETA should consider at least:

* current queued workload
* preparation time
* number of active orders
* kitchen capacity
* order position
* item complexity where available

Conceptually:

ETA ≈ current workload / active preparation capacity + new order preparation requirement

Do not claim this is mathematically perfect.

Design it so the algorithm can later be replaced with an ML model.

The frontend must display:

* current position
* estimated preparation time
* estimated ready time
* current kitchen workload

---

# 13. QUEUE OPTIMIZATION

Do not blindly use FIFO for every operational decision.

Implement a fair priority mechanism that can consider:

* waiting time
* preparation complexity
* pickup deadline
* order age
* operational urgency

Use an aging mechanism so older orders cannot be indefinitely starved.

The algorithm must be documented.

The system must preserve operational fairness.

---

* atomic updates
* constraints
* appropriate locking/concurrency strategies
